# SEO

Everything search engines and social previews see — the document head, `robots.txt`,
`sitemap.xml` and the Open Graph card — is generated at build time, not written by hand.
Two Python scripts under `tools/seo/` produce it, running in a dedicated stage of
`frontend/Dockerfile` that only the production image builds.

## Inputs

| Input            | Source                    | Where it's read                                                                                                    |
| ---------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Canonical domain | `SITE_URL` build argument | `frontend/Dockerfile`, passed from `SITE_URL` in the root `.env` via `docker-compose.prod.yml`                     |
| Site owner       | The production seed       | `database/prod-initdb.d/500_prod_seed.sql`, read directly as SQL text — the generator never connects to a database |

`generate_seo.py` parses the seed's `INSERT INTO` statements for `users`, `contact_info`,
`skills`, `job_history` and `education` with a small regex-based SQL reader (`read_rows` in
`tools/seo/generate_seo.py`), rather than requiring a running MySQL instance during the
image build.

## What's generated

| File           | Written to                                  | Content                                                                                                                                                                       |
| -------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.html`   | in place, inside a marked block in `<head>` | `<title>`, canonical link, description, Open Graph and Twitter card meta, JSON-LD                                                                                             |
| `robots.txt`   | build output root                           | An `Allow: /` group for `*` and for each of `Googlebot`, `Bingbot`, `GPTBot`, `ClaudeBot` and `PerplexityBot`, plus a `Sitemap:` line                                         |
| `sitemap.xml`  | build output root                           | The single page the site serves, with today's date as `<lastmod>`                                                                                                             |
| `og-image.png` | build output root                           | A 1200×630 Open Graph card: circular profile photo, name, role, up to three skills, and the domain, drawn with `tools/seo/og_image.py` in the site's own self-hosted webfonts |

The block written into `index.html` is wrapped in `<!-- Generated by tools/seo -->` /
`<!-- End of tools/seo -->` comments. A rerun finds and replaces that block rather than
appending a second one, so the generator is safe to run more than once against the same
build output.

## The JSON-LD graph

The generator writes a schema.org `@graph` with three linked nodes: a `Person`, a
`ProfilePage`, and a `WebSite`, each keyed by a stable `@id` built from the canonical
origin (`build_json_ld` in `generate_seo.py`). Three `Person` properties matter beyond the
obvious `name` and `jobTitle`:

- **`sameAs`** — the contact links that are profiles elsewhere (GitHub, LinkedIn, a
  personal website), excluding any link that resolves back to the site's own host. This is
  what lets a search engine or an LLM crawler resolve "this person" to the _same_ entity
  across the CV site and those other profiles, rather than treating each as unrelated.
- **`worksFor`** — the employer from the job history row with no `endDate`, i.e. the
  current role. Only set when one exists.
- **`alumniOf`** — the institution from the education row with the latest `startDate`.
  Only set when the seed has an education row at all.

Both `worksFor` and `alumniOf` are omitted individually if the seed has nothing to fill
them with; the rest of the graph is still written.

## Omission behaviour

The generator writes nothing — no `index.html` edit, no `robots.txt`, no sitemap, no
card — and exits `0`, if any of the following hold:

- `SITE_URL` is empty, or names a placeholder host such as `example.com`,
  `yourdomain.com`, or any subdomain of one (checked with a regex, not an exact match).
- The seed file doesn't exist or can't be read as UTF-8.
- The seed's `users` table is empty, or the name or title is missing.
- The name or title still holds the template's own placeholder text (`Your Name`,
  `Your Title`).
- The seed's email is a placeholder address ending in `@example.com`, `@example.org` or
  `@example.net`.

Each omission path logs a one-line reason prefixed `seo: omitting the SEO artefacts —`,
which is visible in `docker build` output. This means a checkout with no production seed,
or a deployment that hasn't set `SITE_URL` yet, still builds — the frontend build stage
is untouched, only the SEO stage skips its work.

## Running it by hand

The generator only needs a directory holding a built frontend and a seed file — it has no
other dependency on the rest of the build:

```bash
# From the repository root
npm run build -w frontend               # produces frontend/build

cd tools/seo
pip install --requirement requirements.txt
python generate_seo.py \
  --build-dir ../../frontend/build \
  --site-url your-domain.example \
  --seed ../../database/prod-initdb.d/500_prod_seed.sql
```

`--seed` defaults to `database/prod-initdb.d/500_prod_seed.sql` relative to the working
directory, so it can be omitted when run from the repository root.

## Development never runs this stage

`frontend/Dockerfile` has three stages: `builder` (the plain Vite build), `seo` (this
generator, built from `builder`'s output), and `production` (nginx, built from `seo`'s
output). `docker-compose.yml` targets `builder` directly for the `frontend` service, so
`docker compose up` never invokes the `seo` stage or its Python toolchain — SEO artefacts
exist only in images built with `target: production`, which is what
`docker-compose.prod.yml` selects.
